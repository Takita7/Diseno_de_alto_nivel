--------------------------------------------------------------------------------
0. WHY THIS WAS NEEDED / HOW IT WAS RUN
--------------------------------------------------------------------------------

Earlier this session, `cmake .. -DBUILD_SYSTEMC_MODELS=ON -DBUILD_TESTS=ON`
failed at `find_package(SystemC REQUIRED)`, which was read as "SystemC is not
installed" and left unverified for the rest of the HLS porting work (T021-T023).
That was wrong: SystemC 2.3.4 IS installed on this machine, at
/usr/local/systemc. Two SEPARATE, PRE-EXISTING problems in the project's own
build - unrelated to anything done this session - are what actually broke it:

  1. find_package(SystemC REQUIRED) (CMakeLists.txt:35) asks for a package
     named "SystemC". The installed CMake package registers itself as
     "SystemCLanguage" (Accellera's standard name for their own CMake
     export), not "SystemC" - a naming mismatch, so find_package fails
     regardless of SystemC being present.
  2. Independently, models/systemc/CMakeLists.txt's add_subdirectory(compute_unit)
     (and scheduler/simt_controller/memory/top) reference paths that don't
     exist - the actual directories are models/systemc/src/compute_unit/ etc.
     (confirmed: `ls models/systemc/compute_unit` -> No existe el archivo;
     `ls models/systemc/src/compute_unit` -> exists). This alone would break
     `cmake configure` even with problem #1 fixed. Likely a leftover from an
     incomplete repo reorganization (git log shows a "Reorder repo" commit).

Given both, the project's own CMake build cannot currently build the SystemC
model at all, independent of this session's HLS work. Fixing the CMake setup
was out of scope for "run the regression tests", so instead: compiled the
relevant .cpp files directly with g++ against /usr/local/systemc (same
technique used all session for the HLS-side tests), bypassing the project's
CMake entirely.

Toolchain: g++ 13.3.0, -std=c++17, SystemC 2.3.4 (/usr/local/systemc),
GTest built from vendored source at
/usr/local/MATLAB/R2026a/sys/ros2/glnxa64/ros2/src/gtest_vendor (same source
used for all tests/hls/* binaries this session - no system GTest package is
installed either).

--------------------------------------------------------------------------------
1. PRE-EXISTING TEST-INFRASTRUCTURE BUGS FOUND AND FIXED
--------------------------------------------------------------------------------

All of the following predate this session and are unrelated to the T021-T023
HLS porting work (confirmed via `git status` before touching anything: models/
systemc/ and tests/systemc/ were completely untouched by this session until
this regression-testing pass). Fixed because otherwise the existing official
tests do not compile/run at all. Each is a small, mechanical fix; no test logic
or assertions were changed beyond what was needed to run at all.

  a) tests/systemc/test_scheduler.cpp:7 and tests/systemc/test_pipeline.cpp:8
     had a stale relative include ("../../models/systemc/scheduler/..." /
     ".../top/top.h") missing a "src/" path segment that the actual current
     repo layout has (models/systemc/src/scheduler/, models/systemc/src/top/).
     Fixed by inserting the missing "src/" segment. (2 files, 1 line each.)

  b) tests/systemc/test_pipeline.cpp called `top.launchKernel(4, 1)` (5 call
     sites) - the CURRENT GPGPUTop::launchKernel signature requires a 3rd
     argument (`std::vector<Instruction> program`, no default), added at some
     point after this test file was last updated. Fixed by passing
     `kernels::intSaxpy()` (an existing kernel from kernel_programs.h, not a
     new invented one) as the program argument at all 5 call sites, plus
     adding the `#include ".../common/kernel_programs.h"`.

  c) tests/systemc/test_pipeline.cpp never called `sc_core::sc_start()` before
     `launchKernel()`. GPGPUTop::launchKernel() does an IMMEDIATE
     sc_event::notify(), which SystemC disallows during elaboration (throws
     E521). models/systemc/test/regression_test.cpp (the working, comprehensive
     test - see section 3) shows the correct pattern: a zero-time
     `sc_core::sc_start(sc_core::sc_time(0, sc_core::SC_NS));` right after
     constructing the top module, before any launchKernel() call. Added the
     identical zero-time sc_start() to all 5 TEST_F bodies in test_pipeline.cpp.

None of (a)/(b)/(c) touch models/systemc/src/ (the actual golden model
implementation) - only the test files themselves.

    passes cleanly. The remaining 4 all fail identically with:
        Error: (E529) insert module failed: simulation running
    This is a STRUCTURAL incompatibility between this test file's design and
    how SystemC works: SystemC's simulation kernel is a process-wide
    singleton - once ANY test has called sc_start(), no LATER test in the
    same process can construct a fresh sc_module hierarchy (each TEST_F here
    constructs its own `GPGPUTop top(...)`). GTest runs all TEST_F cases in
    one process by default, so only the first TEST_F in the whole binary can
    ever succeed at constructing+running a GPGPUTop; every subsequent one
    fails at construction, not at anything the compute pipeline does. Fixing
    this properly would mean restructuring the test file (e.g. one shared
    GPGPUTop instance across all cases, or one TEST_F with multiple
    sub-checks) - out of scope for "run the existing tests", so left as-is
    and documented here rather than patched further.

    this session). So the *hit/miss counts* will legitimately differ between
    the golden model and the HLS port for a kernel with more locality than
    memoryRoundTrip's one-word-per-thread pattern - functional (data)
    correctness is the parity bar, not hit-rate, exactly as already written
    into the interfaces doc.

  tests/hls/test_memory_pipeline.cpp (shared memory bypass,
  write-through/no-write-allocate)
    Golden evidence: Phase 1a/1b/1c/1d/1e directly exercise
    MemoryHierarchy::loadWord/storeWord/loadSharedMemory/storeSharedMemory
    and invalidateCache() with exact value checks (0xDEADBEEF round-trip,
    L1 hit latency==1, miss-after-invalidate, shared memory independent of
    global memory, no address aliasing) - all PASS, confirming the exact

--------------------------------------------------------------------------------
5. CONCLUSION
--------------------------------------------------------------------------------

No functional discrepancy was found between the golden SystemC model's actual
execution and the values/semantics this session's HLS port (compute_pipeline.cpp
T022, memory_pipeline.cpp T023) assumed from reading the source. Every hand-
traced assumption checked above is either directly confirmed by an explicit
golden-model register/mask/counter check, or confirmed via an equivalent
instruction sequence elsewhere in the same regression run. One test-coverage
gap was surfaced (2-level nested divergence, section 4) - the golden model
handles it and the HLS port's stack-based design should too, but this wasn't
independently unit-tested on the HLS side; suggested as a follow-up, not fixed
in this pass.

All bugs found and fixed during this run were pre-existing staleness in the
project's OWN test infrastructure (stale include paths, a stale launchKernel()
call signature, a missing elaboration-phase sc_start()) and a broken CMake
build (find_package name mismatch + a directory-path mismatch from an
apparently-incomplete repo reorganization) - none are related to, or caused by,
this session's T021-T023 HLS work. tests/systemc/test_scheduler.cpp and
tests/systemc/test_pipeline.cpp were edited to fix (a)/(b)/(c) above so they
would run at all; models/systemc/src/ (the actual golden model) was not
touched.
